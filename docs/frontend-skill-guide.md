## Imua Frontend — Engineering Skill Guide

This doc captures the **working mental model and conventions** for the Imua frontend. It is aimed at senior engineers (and agents) joining the project and complements the more detailed specs in `docs/`.

---

## 1. Core mental model

- **Bootstrap vs post-bootstrap**
  - **Bootstrap**: Bootstrap contract on **Hoodi**; all staking operations are local to the client chain. **EVM LST** assets support claim/withdraw in this phase; **EVM NST, XRP, and BTC do not** expose claim/withdraw flows. Genesis data is derived from this phase.
  - **Post-bootstrap**: Same proxy upgraded to **ClientChainGateway** (typically on Sepolia or another client chain); cross-chain messaging to Imuachain; full LST withdraw/claim flows and additional cross-chain operations become available.
  - Many components are shared; behaviour switches based on bootstrap status and chain.

- **Chains and contracts**
  - EVM bootstrap chain: **Hoodi** (often forked into Anvil for local/E2E).
  - Contracts:
    - `Bootstrap` (bootstrap phase ledger of deposits/delegations).
    - `ClientChainGateway` (post-bootstrap gateway with LayerZero messaging).
  - Solidity ABIs are generated by `forge compile` into `out/` and imported via `@/out/...`.

- **Data sources**
  - **Bootstrap**: GraphQL indexer tables (`bootstrap_staker_assets`, `bootstrap_delegation_states`) + direct contract reads.
  - **Post-bootstrap**: Imuachain APIs / precompiles (e.g. Assets precompile).
  - The optimistic cache adds a transient overlay on top of these sources during bootstrap.

## 2. Multi-chain, multi-wallet architecture

- **Heterogeneous chains**
  - The app supports **EVM, XRP, and Bitcoin** staking flows, which differ in:
    - Wallet types (EVM wallet, GemWallet, Bitcoin/AppKit).
    - Transport (EVM RPC vs XRPL vs Bitcoin RPC / external services).
    - How deposits/delegations are encoded (contract calls vs memos vs OP_RETURN).

- **Context-driven providers**
  - We use **React context** to inject chain-specific implementations:
    - **Staking service providers**: abstractions over staking operations (`stake`, `delegate`, `undelegate`, withdraw/claim) that are implemented differently per chain/asset type (EVM LST, EVM NST, XRP, BTC).
    - **Wallet connection providers**: abstractions over WalletConnector, binding EVM wallet logic, and dual-wallet flows (XRP+EVM, BTC+EVM).
  - Components and tabs depend on **interfaces**, not concrete chain implementations. Swapping or extending support for a new chain is primarily: implementing a new provider + wiring it into the context.

- **Wallet connection model**
  - Unified **WalletConnector context** exposes:
    - `isReadyForStaking`, `issues` (e.g. `needsConnectNative`, `needsSwitchNative`, `needsConnectBindingEVM`, `needsMatchingAddress`).
    - Network-specific requirements for EVM vs XRP vs BTC.
  - The **Wallet Connection Modal** is issue-driven: it renders CTAs based on the current issues, and delegates the actual connect/switch work to the appropriate provider.
  - Binding EVM wallets (for XRP/BTC) is handled via a separate store and issue types; see `wallet-connection.md` for the full issue graph.

## 3. UI architecture and conventions

- **Next.js + App Router**
  - `app/` uses layouts and nested routes; `RootLayout` wraps providers (Wagmi, React Query, WalletConnector, etc.).

- **Modal-based staking UI**
  - Staking is primarily **modal- and tab-driven**, not page-driven:
    - Users select a token, then perform operations (`Stake`, `Delegate`, `Undelegate`; `Withdraw` only appears post-bootstrap).
    - Amount entry, operator selection, and review are presented in modals as a linear flow.
  - `new-user-flow.md` describes the UX/interaction patterns; **E2E specs** (below) define what is assertable.

- **Design system and styling**
  - Tailwind + shadcn for base components; `imua-design-system.md` defines design tokens and CSS utility classes for common components (modals, buttons, inputs, selection cards).
  - Prefer composable, headless components (e.g. hooks + presentational components) over deeply coupled, monolithic containers.

- **Selectors & testing hooks**
  - Use `data-testid` for any element that:
    - Represents a stable interaction point; or
    - Is hard to select via semantic roles alone.
  - E2E tests prefer:
    - `getByRole` for accessible elements.
    - `getByTestId` for app-specific or complex elements (e.g. staking buttons, operator rows, modals).

## 4. Testing strategy and phases

- **Unit & integration**
  - Use **Vitest** and `@testing-library/react` for:
    - Pure logic (operations, merge functions, validators, transformers).
    - Store and hook behaviour (optimistic cache, wallet stores, staking hooks).
  - See `testing.md`, `optimistic-updates.md`, `state-changes.md` for what the tests encode (e.g. `deposited = withdrawable + delegated` invariants).

- **E2E — phases**
  - E2E is split along **phase** and **chain** axes:
    - **Bootstrap vs post-bootstrap** (high-level).
    - Within **bootstrap**: three sub-phases:
      - **Phase 1 — EVM (current)**: Hoodi bootstrap (imETH, wstETH, NST). Baseline: `e2e-bootstrap-user-flow-spec.md`.
      - **Phase 2 — XRP bootstrap (planned)**: XRPL + binding EVM flows. Future baseline: `e2e-bootstrap-xrp-user-flow-spec.md`.
      - **Phase 3 — BTC bootstrap (planned)**: Bitcoin + binding EVM flows. Future baseline: `e2e-bootstrap-btc-user-flow-spec.md`.
  - The top-level plan and status live in:
    - `e2e-testing-plan.md`
    - `e2e-phase1-evm-progress.md`
    - `e2e-findings.md`

- **E2E — harness**
  - **Playwright** config:
    - `webServer` runs `pnpm run dev:e2e` (via `scripts/dev-e2e.mjs`), which loads `.env.e2e` and sets E2E env vars (e.g. `NEXT_PUBLIC_E2E_MODE`).
    - `globalSetup` / `globalTeardown` manage **Anvil** (start if needed, wait until ready, fund the test wallet via JSON-RPC, stop at the end).
    - Tests run with `workers: 1` and generous timeouts to avoid first-compile flakes.
  - **RPC & API interception**:
    - GraphQL and RPC calls are intercepted with `page.route()` and either proxied (e.g. Alchemy → Anvil) or fulfilled with fixtures.

## 5. Do / Don’t guidelines

- **Do**
  - Use `pnpm` with the existing `pnpm-lock.yaml`; avoid `npm`/`yarn`.
  - Run `forge compile` before `next build` or `tsc --noEmit` so ABI imports from `out/` succeed.
  - Use the existing E2E harness for bootstrap:
    - `pnpm run dev:e2e` + `pnpm test:e2e` locally.
    - JSON-RPC helpers (`anvil_setBalance`, `anvil_setStorageAt`) for funding and state setup.
  - Prefer `data-testid` + `getByRole` over fragile text selectors in tests.
  - Rely on the **per-phase E2E spec docs** when adding new tests:
    - `e2e-bootstrap-user-flow-spec.md` (EVM bootstrap).
    - Future `e2e-bootstrap-xrp-user-flow-spec.md`, `e2e-bootstrap-btc-user-flow-spec.md`.

- **Don’t**
  - Don’t add new `cast` CLI dependencies in E2E setup; use JSON-RPC via `fetch` instead.
  - Don’t mock `useTokenBalance` or other core hooks for E2E when you can manipulate Anvil state instead.
  - Don’t tie tests to ephemeral UI text when a semantic role or `data-testid` is available.
  - Don’t assume withdraw flows are available in bootstrap; respect tab-gating rules from `bootstrap.md` and `e2e-bootstrap-user-flow-spec.md`.
